# XB2-precision — 31% of the first build brief restates one known fact, and its biggest number is silent

**Repo: `life-command-center`.** Small, and it protects what XB1/XB2 just shipped. The build brief is
live and self-running (snapshot 2 was generated by the GitHub Action on the merge, unprompted). Its
**first** output has two precision problems, both measured live 2026-09-15 — and both are precisely the
"monitor nobody trusts" failure the XB1/XB2 prompt was written to avoid.

**Read first:** `docs/os/PLANNED-BACKLOG.md` **XB2-precision, XB2-followup, BRANCH2, SIDEBARGUARD1** ·
`scripts/build-brief-collector.mjs` · `public.lcc_build_brief_db_audit()`
(`supabase/migrations/20260915120000_*.sql`) · `docs/architecture/data-coherence-invariants.md` **I11**.

## (a) The biggest number is measured and never surfaced

The collector already records, in snapshot 2's payload:

```
branches: { "total_remote": 1722, "unmerged": 0 }
```

**No rule fires on `total_remote`.** So the largest single piece of debt in the repo is captured and
silent — the same "recorded but not alerted on" shape as `item_count` before MB2b added
`items_after_cutoff`. Two measured data points so far: **1,718 on 2026-09-14 → 1,722 on 2026-09-15**,
i.e. **growing ~4/day**, which is the number that matters more than the level.

⚠️ **And understand why `unmerged` reads 0 before you "fix" it.** The collector runs in GitHub Actions,
where a fresh clone has **no local branches** — so local branch debt is **unmeasurable from CI by
construction**, and 0 is the honest answer there, not a bug. Do not make the rule read local branches;
it would report 0 forever and look healthy. **`total_remote` is the only branch metric XB can carry.**

Ship: a `branch_debt` rule on `total_remote`, with severity from a **documented, defensible threshold**
(and state the reasoning in the migration comment — an arbitrary number is how a rule gets ignored).
Report the **trend** alongside the level, since growth is the actionable half. Cross-reference **BRANCH2**,
which owns the actual remote cleanup, and note that any prune must exclude the 8 branches BRANCH1 pushed
to preserve local-only work.

## (b) One known gap is inflated into 10 critical findings

`market_brief_lane_stale_or_missing` emits **per lane × section**. With 3 lanes × 5 sections and only
`dialysis` carrying facts, that produces:

| | count |
|---|---:|
| `government` × 5 sections | 5 critical |
| `net_lease` × 5 sections | 5 critical |
| `dialysis/capital_markets` | 1 warn |
| **share of the whole brief** | **11 of 32 findings (34%)** |

Every one of those 10 critical rows restates a single fact already known and tracked: **no producer has
ever written a government or net-lease fact** (MB8; MB9 recorded zero rows under either lane). A brief
where a third of the critical findings are one known gap is on its way to being a brief nobody reads —
and it buries the one genuinely new find in the same snapshot (`SIDEBARGUARD1`).

**Fix: aggregate to one finding per lane**, with the affected sections as detail, and let the existing
backlog row carry the "no producer exists" fact rather than re-deriving it five times.

### ⚠️ Do NOT "fix" the lane list — Cowork got this wrong and it is retracted

The XB reconcile originally claimed the view "reports staleness on a retired lane" because MB9 collapsed
`net_lease`. **That was wrong.** MB9 collapsed **`broad_net_lease` INTO `net_lease`** — `net_lease` is
the **survivor**, and `v_market_brief_staleness`'s lanes (`dialysis`, `government`, `net_lease`) match
`KNOWN_LANES` in `api/_shared/market-brief-render.js` **exactly**. The view is correct. The error was
reading a collapse as a retirement without checking the constant. **The lane list needs no change** —
this unit is aggregation only.

a threshold for `branch_debt` without stating its basis. Don't touch `producer_stall_not_flag_gated` —
it is working exactly as intended (fires on `sidebar_contact_guard`, silent on `p_rss`).
