## 1. What changed

### Route 1: writable definer views
A view with no `security_invoker` over one table is auto-updatable. A view with `INSTEAD OF` triggers is writable too. The write runs as the view **owner**, past the base table's RLS.

Population: `pg_relation_is_updatable(oid, true) > 0`, no `security_invoker`, and anon or authenticated holds INSERT/UPDATE/DELETE. Measured live before the change:

| DB | views |
|---|---|
| dia (10) | `v_sales_feed_portfolio` (the comps spine), `scrub_cache` (INSTEAD OF triggers), `v_dia_broker_company_registry_health`, `v_dia_listing_cap_review_open`, `v_dia_nm_cis_unlinked`, `v_dia_operator_orphan_registry_gap`, `v_dia_operator_unresolved_review`, `v_dia_ownergap2_fabrication_guard_collisions`, `v_dia_place_vocab_state_review`, `v_sf_link_review_queue` |
| gov (7) | `v_ownership_history_portfolio`, `v_gov_agency_registry_health`, `v_gov_county_ingest_worklist`, `v_gov_firm_term_backfill_queue`, `v_gov_place_vocab_state_review`, `v_gov_property_duplicate_group_key`, `v_sf_link_review_queue` |
| LCC Opps (21) | listed in the migration header. Several sit over review tables (`junk_entity_review`, naming hygiene, dup pairs, link review), so an anon write could have set a verdict. |

The fix revokes `INSERT, UPDATE, DELETE, TRUNCATE` from `public, anon, authenticated`. **SELECT is kept on every view.** It is a catalog loop over that predicate, not a name list, so a view created before the apply is caught too. CC counted dia 9 because `scrub_cache` is not auto-updatable (`is_updatable = NO`). It is still writable through its triggers, and `pg_relation_is_updatable(oid, true)` counts it.

The four dia rows marked **public** were not on the prompt's list. They are named "service role" or "authenticated", but they are `TO public`, so anon could write through them. The census found them, and they were fixed in the same change.

What each table received:
- A `sec7_service_role_all_<t>` policy (`FOR ALL TO service_role`).
- A `sec7_client_read_<t>` SELECT policy, only where a dropped `ALL … USING (true)` policy had been a client's read path. It covers **the same roles**. For example, `salesforce_accounts` stays anon-only; authenticated gains nothing.
- A revoke of client INSERT/UPDATE/DELETE/TRUNCATE grants, so a future permissive policy still writes nothing.
- RLS stays on.

Reads that already had their own policy were left alone: `anon_read_it`, `anon_read_fpc`, `ingestor_can_select`, the `Allow anon read …` policies, `anon_read` on `bd_execution_log`, and `anon_select` / `auth_select` on `research_queue_outcomes`.

### Standing guard
`<dom>_sec7_write_path_violations()` is on dia, gov and LCC Opps. It is invoker-rights, service_role-only, and returns one row per:
- `writable_definer_view`: a client role can write through a definer view.
- `client_write_policy`: any public-table policy for public/anon/authenticated whose WITH CHECK is `true`, or which has no WITH CHECK and USING `true`.
- `client_write_grant`: a client write grant on a phase-2a table. dia and gov only.

**It reads 0 live on all three.** The phase-1 `<dom>_sec7_ledger_privilege_violations()` still reads 0.

## 2. Writer inventory (step 1)

The source was `edge_logs`, 2026-09-17..24, one 24h window per call. Role was taken from the JWT `role`, or else the `sb_secret_` / `sb_publishable_` key prefix. On gov, 2026-09-19 12:00–00:00 returned a fetch error on every retry, the same window SEC7-LEDGERS lost.

- **dia: zero** anon/authenticated POST/PATCH/PUT/DELETE on `/rest/v1/*`.
  - The positive control on 09-24 found the real writers, all service_role:
    - python-httpx (the Dialysis pipeline): `facility_patient_counts` PATCH ×235k, `cmbs_loans`, `cmbs_loan_properties`, `ingestion_tracker`, `scrub_cache` (the trigger view), `user_interactions`.
    - Deno edge functions: `salesforce_accounts` POST ×300.
  - Code check for writers too rare for the window:
    - `lead-ingest` (on dia) writes `marketing_leads` / `loopnet_listing_map` with a secret named `DIA_SUPABASE_KEY`. That name historically held the anon key (issue #720). Its last writes, 2026-08-30/31, carried key prefix `sb_secret_`, so **it is service role**. No change was needed.
    - The Dialysis Python client prefers `SUPABASE_SERVICE_ROLE_KEY`, and every logged request from it is service_role.
- **gov: zero** anon/authenticated writes.
  - `property_sale_events` / `research_queue_outcomes` are written by LCC `detail.js` → Railway proxy → `govSupabaseKey()`, which is service_role on every Railway request logged.
- **LCC Opps**: the only anon writes are Power Automate → `POST rpc/lcc_record_flow_failure` (7 calls, two workflows). That is a function, untouched here. There were zero client writes to any `v_*` path.

**No legitimate writer used anon or authenticated, so no writer was re-routed and nothing broke.**

## 3. Verification (live, rolled back)
