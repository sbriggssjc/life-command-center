## What shipped

### 1. Server-side discovery, extended to Listing__c + Deal (`?action=discover`)

`supabase/functions/intake-salesforce-files/index.ts` gains an `?action=discover`
action (pure logic in the node-testable `discovery.ts`) that, via the existing
Salesforce Connected App (`getSfToken`, already used by `?action=fetch`):

- reads staged Comp/Listing/Deal SF ids (`sf_comp_staging` / `sf_listing_staging`
  / `sf_deal_staging`), or a scoped `entity_ids[]` list;
- queries `ContentDocumentLink WHERE LinkedEntityId IN (...)` (chunked 200/query,
  the bounded form Salesforce requires), then the **latest `ContentVersion`** per
  document;
- filters to document types (pdf/docx/xls — thumbnails/images excluded);
- **dedup contract:** skips any `content_version_id` already in `sf_files`
  (`sha256` is the second dedup key, recorded at fetch time);
- inserts new rows `ingestion_status='discovered'` with `linked_entity_type` +
  `linked_entity_sf_id` **and the stamped `sf_comp_id` / `sf_listing_id` /
  `sf_deal_id` traversal column**.

This is a **clean no-op (`200 configured:false`)** when the Connected App is not
configured, so a driving cron is safe. Files then flow through the **existing**
`?action=fetch` (bytes → `salesforce-files` bucket) and `?action=stage-queued`
(→ LCC `/api/intake/stage-om` extraction) — **no new extraction engine.** The
Power-Automate `?action=manifest` path was also updated to stamp the same
traversal column, so both discovery front doors are consistent.

### 2. Additive schema — `sf_files` traversal columns (applied live, gov + dia)

`sf_files` gains `sf_comp_id`, `sf_listing_id`, `sf_deal_id` (+ partial indexes).
The existing 588 gov / 1,448 dia `Comp__c` rows were backfilled
`sf_comp_id = linked_entity_sf_id` (gov verified 588/588). Additive, nullable,
reversible (`DROP COLUMN`).

### 3. Resolver traversal (`api/_handlers/om-comp-resolver.js`)

`findOmFilesForReview` now matches an `sf_files` row whose **`linked_entity_sf_id`
OR any traversal column** is one of the comp's SF ids — so a Listing- or
Deal-attached OM is reachable through the comp → `sf_comp_staging.sf_listing_id`
→ `sf_files` path, not only via a Comp-attached file.

### 4. Discover cron (apply-AFTER edge redeploy)

`sf-files-discover-hourly` migrations for gov + dia (**not applied live** — they
schedule the new action, so per deploy-ordering they are applied only after the
edge function is redeployed). Runbook below.

## Honest ceiling / realization gate

Like the SOS / SAM / county-ingest units, the mechanism is the durable fix;
realizing value is **egress + credential gated**:

1. The CI sandbox has **no Salesforce egress**, so the live "Fort Wayne OM appears
   in `sf_files`" step runs post-deploy on the Supabase edge runtime (which does
   reach Salesforce), not here. The acceptance is proven by a **real-id/real-figure
   fixture**, exactly as W3.7's Fort Wayne case was.
2. `?action=discover` requires the SF Connected App creds (`SF_INSTANCE_URL` /
   `SF_CLIENT_ID` / `SF_CLIENT_SECRET`) on the gov/dia edge env. Until set it is a
   clean no-op. (No `discover`/`fetch` cron exists today — server-side SF pull is
   net-new here.)
