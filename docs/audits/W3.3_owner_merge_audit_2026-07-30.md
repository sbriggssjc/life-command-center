# W3.3 — Retire the dangerous owner mergers (audit + fix)

**Date:** 2026-07-30 · **Branch:** `claude/gov-owner-merge-resolver-tx0taq` · **DBs:** gov `scknotsqkcheojiaewwh`, LCC Opps `xengecqvemvfknjvbvrq`

Two auto-writers contradicted the ORE's evidence standard (audit 3.2.1 / 3.2.2). Both are now
gated; the historical output of the first is audited into a reversible unmerge worklist.

---

## Unit 1 — `owner_merge_tick()` (gov)

### The defect
`owner_merge_tick()` (gov migration `20260524110000`) hourly auto-merges `recorded_owners`
that share **`canonical_name`**. `compute_canonical_name()` greedily loop-strips trailing
legal-ish tokens **including `CO` / `COMPANY`**, so genuinely different owners collapse to one
canonical and get merged (properties / sales_transactions / SF accounts follow the survivor via
`apply_owner_merge()`, which logs only the (loser, survivor) pair — not which FK rows moved, so
the collapse is effectively irreversible).

### The fix (migration `20260730130000_gov_W33_owner_merge_tick_strict.sql`, applied live)
- **`gov_owner_strict_core(text)`** — a stricter normalizer (the ORE `lcc_institution_norm`-style
  check). It removes all non-alphanumerics (so `"L.L.C."`≡`"LLC"`, `"A.J.M.D."`≡`"AJMD"`,
  `"B & B"`≡`"BB"`) but strips **only pure legal-entity forms** (LLC/LLP/LLLP/LP/LTD/LIMITED/INC/
  INCORPORATED/CORP/CORPORATION/DST) — it **keeps** CO / COMPANY / GROUP / PARTNERS / PARTNERSHIP
  / HOLDINGS. Bleed-prone short forms (`pllc/plc/pa/pc/lc/na`) are deliberately excluded so
  `"X Group LLC" == "X Group"` instead of falsely routing to review.
- **Hardened `owner_merge_tick(p_dry_run boolean DEFAULT false)`** — same candidate pool
  (`canonical_name` groups with >1 unmerged member) but each (survivor, loser) pair is now gated:
  auto-merge **only** when the two names share `gov_owner_strict_core` (i.e. they differ solely by
  a pure legal form); otherwise the collapse stripped a semantic token (">1 token stripped") and
  the pair is **routed to the W3.2 owner-reconcile lane** (`entity_match_candidates`,
  `match_method='owner_merge_tick_strict_review'`) + logged to **`gov_owner_merge_review_log`**
  instead of merging. The existing cron `lcc-gov-owner-merge-tick` (`0 * * * *`,
  `SELECT public.owner_merge_tick();`) resolves to the new all-defaulted signature unchanged.

### Grounded findings
- **`uq_recorded_owners_canonical`** is a UNIQUE index on `(canonical_name, COALESCE(state,''))`,
  so two *unmerged* recorded_owners with the same canonical + same state cannot coexist. The tick
  therefore only ever fires on **cross-state** canonical collisions.
- **The tick itself has merged 0 rows** (`dq5_owner_merge_log` has no `row_pk='owner_merge_tick'`
  rows). It has been dormant since the May-2026 bulk A1/C4 remediation collapsed the backlog. The
  hardening is therefore **preventive** (a dry-run over today's data = 0 merges / 0 routes).
- **Synthetic gate (self-rolled-back, 0 residue):** two same-canonical/cross-state pairs —
  `"…Beta LLC"`/`"…Beta Inc"` (strict cores equal) **merged (1)**; `"…Alpha Company"`/`"…Alpha Co"`
  (strict cores differ) **routed to review (1)**, filing 1 `entity_match_candidates` + 1
  `gov_owner_merge_review_log` row.

### The 2 ORE candidate-mode auto-merges (honest scoping)
`lcc_reconcile_owner()` (LCC Opps) is **read-only** (STABLE) — it scores/verdicts, it never merges.
The "2 candidate-mode auto-merges" cited by the W3.2 correction were **LCC-Opps `entities`** merges
performed by the pre-W3.2 JS reconcile driver (`source=candidates`, `doMerge` defaulted true), a
**different table/DB** than gov `recorded_owners`. W3.2 already neutralized that path (engine
rescheduled verdicts-only, merge=0; PR #356). They are **not reversible from a gov migration** and
belong to the W3.2 `owner_reconcile` lane / `entity_match_labels` (and W3.4), not this gov unit.
Data point: **28 of 31** gov-domain LCC-entity merges dated 2026-07-30 have differing
`lcc_institution_norm` cores (e.g. `"STAG Industrial, Inc." → "STAG INDUSTRIAL HOLDINGS, LLC"`) —
those are LCC-entity review candidates for the W3.2 lane, tracked separately from this worklist.

## Unit 2 — gov recorded→true owner resolver (`sidebar-pipeline.js`)

### The defect
`ensureTrueOwner()` (gov branch) resolved the true owner via
`true_owners?canonical_name=ilike.*<normalized>*&limit=1` — an **unanchored substring, first-row-
wins, no threshold** query that was the **sole source of gov `true_owner` links**. A short
incoming name (`"Smith"`) substring-matched an unrelated existing owner (`"Smith Medical Holdings"`)
and silently linked the property to the wrong true owner.

### The fix
- **Exact-normalized match auto-links.** Compute `govOwnerStrictCoreJS(name)` (JS mirror of
  `gov_owner_strict_core`); bounded-fetch existing `true_owners` by leading token
  (`limit=40`, `merged_into_true_owner_id IS NULL`); if **exactly one** candidate has an equal
  strict core → link to it.
- **Never link from a substring hit.** On a non-exact (0 exact, or >1 ambiguous) result, the
  incoming owner is **created fresh** (property links to the NEW row, never the substring hit) and
  the best existing candidate is filed to **`entity_match_candidates`**
  (`match_method='costar_true_owner_fuzzy'`, `similarity` = Dice bigram score, `status='pending_
  review'`, deduped) for a human merge through the W3.2 lane.
- Tests: `test/gov-true-owner-resolver.test.mjs` (4) + 33 existing sidebar/owner tests pass.

## Reversibility ledgers
- `public.gov_owner_merge_unmerge_worklist` — historical false-merge candidates + `reactivate_sql`.
- `public.gov_owner_merge_review_log` — every future collapse the tick declines to merge.
- `entity_match_candidates` — both units file review pairs here (W3.2 lane); reversible by resolving.
- Loser `recorded_owners` / `true_owners` rows are **soft-merged** (`merged_into_*` set), never
  hard-deleted.
