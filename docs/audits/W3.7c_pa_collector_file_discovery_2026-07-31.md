# W3.7c — Listing/Deal OM discovery via Power Automate collector (2026-07-31)

**Unit:** W3.7c (replaces W3.7b's unusable Connected-App server-side sweep).
**Doctrine:** the Northmarq org is SSO-gated and **cannot provision a Salesforce
Connected App** (no admin; a client-credentials login returns
`INVALID_SSO_GATEWAY_URL` — `SALESFORCE_LCC_INGESTION_PLAN.md` §2). W3.7b's
`?action=discover` / `?action=fetch` read `SF_CLIENT_ID`/`SF_CLIENT_SECRET`, so
they were **inert forever**. **STANDING ARCHITECTURE RULE:** all Salesforce
reads/fetches flow through Power Automate → `X-PA-Webhook-Secret` edge endpoints;
never request `SF_CLIENT_ID`/`SF_CLIENT_SECRET` or Connected-App provisioning. PA
is transport only; it never writes a domain table.

---

## What shipped

Converts W3.7b's insert logic (`discovery.ts`) to the **PA-collector** pattern:
Power Automate holds the interactive-SSO Salesforce connection, reads
ContentDocumentLink/ContentVersion, and POSTs metadata + bytes to three new edge
webhook actions on `intake-salesforce-files` (deployed on Dialysis_DB, reaches
gov + dia via env vars). The same `sf_files` dedup contract (content_version_id)
and the same downstream fetch→extract chain are reused — only the transport
changed (PA instead of a Connected App).

### 1. `GET ?action=discovery-worklist` (webhook-secret auth)

Returns a batch (`?limit=`, default 200, cap 1000, split across domains) of
staged **Comp/Listing/Deal** SF ids — **both domains** — that
(a) have **no `sf_files` row** (checked on the traversal column OR
`linked_entity_sf_id`), and (b) have **no discovery attempt in `?stale_days=` N
days** (default 7). It **stamps `last_file_discovery_at=now()` on every served
id** (a lease) so an id that yields no files is not re-served every run
(thrash-guard); an id that later gains an `sf_files` row drops out via (a)
regardless. Each item carries `{vertical, object_type, sf_type,
linked_entity_sf_id}` so PA needs no re-derivation and echoes `vertical` back.

### 2. `POST ?action=discover-webhook` (webhook-secret auth)

Accepts PA's array of `{linked_entity_type, linked_entity_id,
content_document_id, content_version_id, title, file_name, extension,
version_number, size_bytes, vertical?}` → maps each via the shared
`mapDiscoveredFileToRow` (stamps the `sf_comp_id`/`sf_listing_id`/`sf_deal_id`
traversal column, rejects non-document extensions + malformed ids), **dedups on
`content_version_id`** (`filterNewVersions`, the same contract the retired sweep
used), routes each file to gov/dia, and inserts `ingestion_status='discovered'`
rows. Idempotent; reports `discovered`/`skipped_existing`/`skipped_invalid`.

### 3. `POST ?action=file-content` (webhook-secret auth)

Accepts `{content_version_id, sha256?, file_base64, vertical?}` → verifies
**sha256** (mismatch → HTTP 422; corrupt bytes never reach the extractor) and a
**15 MB size cap** (over → 413 with the `?action=upload-url` large-file lane
pointer), writes bytes to the `salesforce-files` bucket, and flips the row to
`ingestion_status='stored'` / `extraction_status='queued'` — feeding the
**existing** `sf-files-extract-queued-hourly` cron → `?action=stage-queued` →
`/api/intake/stage-om` (no new extraction engine). **Idempotent on
`content_version_id`**: a row already `stored` is a no-op (never re-extracts).

### 4. Connected-App path retired (tombstone)

`getSfToken()` / `sfQuery()` / `sfDownloadBytes()` and the `SF_INSTANCE_URL` /
`SF_CLIENT_ID` / `SF_CLIENT_SECRET` env reads are **deleted** from
`intake-salesforce-files/index.ts` (replaced by a tombstone pointing at this
doctrine) so no dormant-capability flag that can never turn on remains.
`?action=discover` / `?action=fetch` now return **HTTP 410** with the
PA-collector replacement. The two never-applied `*_sf_files_discover_cron.sql`
migrations (which scheduled the retired `?action=discover`) are removed — the
live cron set was verified to hold only `sf-files-extract-queued-hourly` (the
discover cron was never scheduled live).

### 5. Additive schema — staging attempt lease (applied live, gov + dia)

`last_file_discovery_at timestamptz` on `sf_comp_staging` / `sf_listing_staging`
/ `sf_deal_staging` (+ partial index), applied live to gov
(`scknotsqkcheojiaewwh`) and dia (`zqzrriwuavgrquhisnoa`) BEFORE the edge deploy
(additive-schema-before-writer ordering). Additive, nullable, reversible.

## The PA flow

`docs/flows/FLOW_sf_file_discovery.md` (full spec, matching
`POWER_AUTOMATE_UPDATE_GUIDE.md` conventions) + `flow-sf-file-discovery.json`
(skeleton). Scheduled weekly: HTTP GET worklist → per id, Salesforce connector
reads ContentDocumentLinks + latest ContentVersion → filter to doc extensions →
HTTP POST discover-webhook (batched 200) → per new file, Get VersionData → HTTP
POST file-content. Webhook-secret header on every LCC call; SF/PA limits
respected (bounded CDL filter, per-item concurrency, batched POSTs).

## Honest ceiling / realization gate

Like SOS / SAM / county-ingest, the **mechanism** is the durable fix; realizing
value is **operator-gated** — Scott must build the PA flow from the spec (using
the existing interactive-SSO Salesforce connection). The CI sandbox has no
Salesforce egress, so live "Fort Wayne OM appears in `sf_files`" runs post-build
on Scott's PA tenant, not here. There is **no credential to provision** (that was
the whole point of retiring the Connected-App path) — only the flow to build.
